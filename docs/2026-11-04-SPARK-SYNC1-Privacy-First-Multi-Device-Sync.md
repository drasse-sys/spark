# Spark SYNC1 — Privacy-First Multi-Device Sync V1

Status: **implementation candidate on an isolated branch. Not merged, not deployed. Default OFF.** No Cloudflare resource, database or secret has been created. Production configuration and behaviour are unchanged: production has no `SYNC_DB` binding and no `SYNC_ENABLED`, so every `/sync/*` path answers 404 there exactly like an unknown route.
Baseline: `main` at `f4f55af9fd72c5f30a7dc9ade97a01cefa06c48a` (INT1).

## 1. Goal and non-goal
The same child can use Spark on several family phones. Structured learning progress converges. No phone can silently erase newer progress from another. Offline use keeps working, and sync failure never blocks homework. Existing single-device users and Trusted Backup (TR1) keep working. Raw conversations and photos are never uploaded. A server compromise exposes as little child data as practical.

The goal is **not** "sync everything". V1 syncs the smallest domain that gives continuity: profile basics, learning evidence and its derived mastery, the word list, and bounded session summaries.

## 3. Threat model

| Threat | V1 outcome |
|---|---|
| **Stolen phone** | The thief has the local data (already true today), the device token and the sync key. Until the parent revokes the phone, it can still read the family's synced data and write evidence. It **cannot** revoke other phones, delete children or reset the family: those need the family code, which phones do not store. After revocation it gets 403 and cannot re-enrol (revocation is permanent for that device id), and re-pairing needs the family code. There is no remote wipe. To also make the stolen key useless against a future server leak, the parent rotates it with "Start på nytt med ny nøkkel". |
| **Stolen device token only** | It cannot enrol for sync without the family key: enrolling needs a membership proof derived from the key. If the token belongs to an already enrolled phone, the thief can download ciphertext and upload records. Uploaded records that do not authenticate are skipped by every phone. Revoke the phone. |
| **Family code disclosed** | The holder can pair a new device, revoke phones, delete the server copy of a child, and reset the family's server data. These are availability attacks. They **cannot** read synced data, because the code gives no key. They **cannot** delete local data: a tombstone must authenticate under the family key, and phones keep an unverifiable deletion as a local copy. Rotate `FAMILY_CODE`. |
| **Malicious paired device with the key** | It is inside the trust boundary, as with TR1. It can write arbitrary evidence and inflate mastery, and it can edit profiles. It cannot delete or revoke without the family code. |
| **Worker compromise** (code, secrets, D1) | Exposed: that a family exists; device ids, enrolment dates and last-seen days; the number of children; record counts, kinds (`base`/`op`/`tombstone`) and Worker receive times (which show when phones uploaded); ciphertext sizes in 256-byte buckets; the SHA-256 of the membership proof. An active attacker also sees membership proofs at enrolment. A proof is an HKDF output: it does not reveal the encryption key. **Not exposed:** names, ages, interests, answers, skills, words, session summaries. The attacker can withhold, delete or re-sequence records (availability and consistency) and can mint tokens. It cannot forge, modify, swap or replay a record into a valid state (§6). |
| **D1 read compromise** | As above, without the active capabilities. |
| **Rollback or replay of old state** | A record id already seen by a phone is ignored. A payload moved to another id, child, kind or generation fails AES-GCM authentication. A phone never discards local data because the server sent less. An older server state cannot shrink a phone's state, because records are only added. A brand-new phone can be served a stale but authentic subset. Without client-signed heads this is not detectable (§11). |
| **Forged client** | The same as a malicious device: it is inside the trust boundary. All inputs are schema-checked on both sides, so it cannot inject properties or crash other phones. |
| **Device clock manipulation** | See §7.3. Delay credit can never exceed what the recording phone granted. A phone whose clock disagrees with the Worker at upload, or that claims a time after receipt, gets its records placed at the Worker receive time with no delay credit. Records cannot be placed before the phone's last sync. |
| **Concurrent offline edits** | Evidence is a union of immutable events. Derived state is recomputed. Profile fields are last-writer-wins by effective time. Word removal is scoped to the word ids the removing phone knew (§7). |
| **Duplicated / restored device** (cloned storage) | Record ids are random, not counters, so clones never collide. Identical queued records deduplicate by id. A phone rolled back to an older copy of its own storage re-downloads, deduplicates and converges. |
| **Deleted child** | A tombstone plus a permanent `deleted` status. Records for that id are refused forever, so an old offline phone cannot resurrect the child (§8). |
| **Cross-family leakage** | Every row carries `family_id`, derived on the Worker as an HMAC of a fixed label under `DEVICE_SIGNING_SECRET`. It never comes from a request. Every query is scoped by it. A token from another family fails signature verification. Tested with two families on one shared database, plus a negative control that removes the scoping. |
| **Enumeration** | Child, record and generation ids are 128-bit random values. Device ids are UUIDv4 values from the token. An unknown child id gets the same answer whether it exists in another family or nowhere. |

### What V1 protects
- Confidentiality of synced learning content against the Worker, D1, Cloudflare account access and network observers, provided the phones and the app code are not compromised.
- Integrity and authenticity of every synced record against anyone without the family key, including the Worker.
- No family-wide destructive action without the family code. No destruction of local data by anyone without the key.
- Convergence: phones holding the same records compute byte-identical state (property-tested).
- No mastery inflation from merging. No delay credit beyond what the recording phone granted.

### What V1 does not protect
- A phone or a key holder acting maliciously. The client is the trust boundary, exactly as in TR1.
- Availability against a compromised Worker or a family-code holder.
- Detection of withheld records on a brand-new phone.
- Metadata: activity timing, counts and sizes are visible to the Worker.
- Compromise of the GitHub Pages app code. Malicious app code could exfiltrate the key.
- **Not forward secrecy.** A revoked phone that keeps the key can decrypt any ciphertext it obtains later until the key is rotated.

## 4. Storage choice: **D1** (one database, isolated `sync-lab` environment)

| | D1 | Durable Objects | KV |
|---|---|---|---|
| Consistency | Serialized SQLite writes, transactional `batch` | Strong, single-writer per object | Eventual (up to about 60 s); no compare-and-swap |
| Ordering / idempotency | Per-family sequence and `UNIQUE(family_id, record_id)` inside one transaction | Possible, but hand-built | No atomic multi-key writes; LWW per key |
| Revocation / tombstones | Read-your-writes | Yes | A stale read can serve a revoked device or miss a tombstone |
| Offline merge | Server is a relay; merging happens on the client | same | same |
| Queries | Range by sequence; parent admin through SQL (`wrangler d1 execute`) | Custom code, no console | List by prefix (eventual) |
| Ops / migration | Versioned SQL migrations; Time Travel restore | Class + migration tags; data opaque to tooling | Simple, but wrong semantics |
| Cost at family scale | Free tier, far from limits (§13) | Free tier with SQLite DOs | Free tier |
| Privacy | Ciphertext + minimal metadata | same | same |
| Testability here | Real local D1 via workerd (`getPlatformProxy`) in Node and Chromium tests | Needs a DO harness | Easy, but cannot show the needed guarantees |

**Why D1:** the relay needs exactly four things. A gap-free per-family order. Idempotent inserts. Conditional writes that re-check revocation, deletion and generation inside the transaction. A small SQL surface the parent-operator can inspect. D1 gives all four. Because each family runs its own Worker, the main advantage of Durable Objects (an object per tenant) buys nothing here, while it would add a class, migration tags and harder testing. KV is rejected because eventual consistency breaks revocation, tombstones and cursor completeness. No multi-storage abstraction was built.

## 5. Privacy / encryption decision: **hybrid — end-to-end encrypted payloads, minimal server-readable metadata**

Compared options:
1. **Server-readable structured state.** Simplest. But a Worker or D1 compromise exposes the child's whole learning history. The privacy cost is not needed, because the server never has to read content (merging happens on the client, §7).
2. **Fully client-encrypted state blobs.** The server cannot authorize per child, order records or keep tombstones. Each phone would upload whole-state blobs, which forces last-writer-wins on state. That is exactly what destroys independent progress.
3. **Hybrid (chosen).** Every payload is ciphertext. The server sees only what it needs to authorize and order: family, device, child id, record id, kind, sequence number, receive time, a clock flag and size.

Because the merge model is an append-only event log folded deterministically on each phone, end-to-end encryption costs little extra complexity, and it gives the largest real privacy gain available.

**Key ownership and distribution (exact):**
- **Family sync key:** 128 random bits, generated with `crypto.getRandomValues` on the phone that starts sync. It is shown once as 28 Crockford-base32 characters in 7 groups (`XXXX-…`). The last 2 characters are a 10-bit SHA-256 checksum, so a typing error is caught on the phone. The parent types it on each other phone. It is stored in `spark_sync` (localStorage), like the device token. It is never sent to the Worker, never put in backups and never logged.
- **Derivation:** HKDF-SHA-256 (salt `SPARK-SYNC-V1`). `info="enc"` gives an AES-256-GCM key (non-extractable `CryptoKey`). `info="member"` gives a 256-bit membership proof. The Worker stores only `SHA-256(proof)`.
- **Encryption:** AES-256-GCM with a random 96-bit IV for each record. The plaintext is padded to 256-byte buckets. The associated data is `SPARK-SYNC-V1 \n generation \n child \n kind \n record id`. Only standard Web Crypto primitives are used.
- **Enrolment:** a device token (family code, at pairing) plus the membership proof (key). Starting a family additionally needs the family code.
- **Rotation / lost key:** "Start på nytt med ny nøkkel" (family code). It deletes everything the family stored on the Worker and starts a new generation under a new key. Each phone keeps its data. Previously shared children become local copies. The resetting phone shares its children again under new ids, and the other phones join with the new key. V1 does not re-encrypt in place (§17).
- **New phone:** pair with the family code, then enter the sync key. Everything arrives.
- **All phones lost:** the parent's written-down key plus the family code recover everything on a new phone. Without the key the server copy is unreadable by design. Trusted Backup files remain an independent recovery path.
- **Trusted Backup interaction:** none in the key model. Backups contain no key and no sync data.

Why this tradeoff is acceptable: the extra burden is one 28-character code per extra phone. Anything weaker (a key derived from the family code, or a key wrapped by it) would put the key within reach of the Worker, which holds `FAMILY_CODE`. That would void the main protection.

## 6. Family / device / child identity
- **Family namespace:** `family_id = base64url(HMAC-SHA256(DEVICE_SIGNING_SECRET, "SPARK-SYNC-FAMILY-V1"))`. It is one per deployment, derived only on the Worker, and stable across `FAMILY_CODE` rotation. Rotating `DEVICE_SIGNING_SECRET` (which re-pairs every phone anyway) starts a fresh namespace.
- **Family generation:** a random id created by "create" and "reset". It is bound into every ciphertext's associated data. A phone on an old generation gets 409 and must join with the new key.
- **Device identity:** the `deviceId` inside the existing Worker-signed token. TR1's token model is unchanged and `/chat` is untouched. Sync adds a server-side registry row per family (`active` or `revoked`).
- **Child identity:** a random 128-bit id, assigned when a parent shares the child. It is persisted in the same atomic `spark_kids` write as the share and never changes afterwards. Display names are never identities. Existing local children get their id at the moment they are shared. Unshared children keep working exactly as before and need no id.
- **Discovery on a new phone:** after joining, the phone downloads the family log. Each child begins with its encrypted base record, and that record creates the child on the phone. If the phone only has the empty starter profile, the first family child replaces it.
- **Is the family code enough to join?** No. Pairing needs the family code, and sync membership needs the key. Each covers what the other cannot.
- **Revocation:** done by any enrolled phone together with the family code. It is permanent per device id. A revoked phone keeps its local data and gets a clear status. It keeps chat access, which is governed by the existing token and `REVOKE_BEFORE` (§17).
- **Trust root:** sync talks only to `DEFAULT_SERVER_URL`, the Worker the app build ships with. It runs only when the phone is paired with that Worker (as TR1 signing does), with `redirect:'error'`. The ⚙️ server address is never used. The server is a relay, not an authority: integrity comes from the key.

## 7. Merge / convergence model

### 7.1 Records
| Server kind | Payload types (inside the ciphertext) |
|---|---|
| `base` | Genesis snapshot of a child when shared: profile, plus learning as the phone holds it (skills, words, totals; sessions travel separately). Exactly one per child, enforced by the Worker. |
| `op` | `skill` (the observed input of one `L.event` and the delay credit the recording phone granted), `word-add`, `word-review`, `word-remove` (explicit ids), `helped`, `session` (summary), `profile` |
| `tombstone` | `{child, t}`, created only by the family-code-gated delete |

### 7.2 Fold
A child's state is: its base, then its other records sorted by `(orderKey, Worker sequence, record id)`, then this phone's unsent changes in local order. `orderKey = max(effectiveTime, receiveTime − 14 days)`, and the base always sorts first. Every input is record data or Worker metadata, so every phone holding the same records computes the same state, whatever order the records arrived in. For uploads within 14 days of recording, the fold is in true time order, independent of upload order. This is tested both ways (A-first vs B-first) and with 20 shuffles.

**Local checkpoints keep phone storage bounded.** After a complete download, every record with `orderKey ≤ WorkerNow − 14 days − 1 day` is final: any record that arrives later sorts after it. Those records are folded into a checkpoint and dropped from the local log. Since a checkpoint is a prefix of the same sequence on every phone, a phone with checkpoints equals a fresh phone that replays everything (tested).

### 7.3 Field classification
| Behaviour | Fields |
|---|---|
| **Append / union** (immutable, deduplicated by record id, and by evidence id in `L.event`) | skill evidence and observations, word reviews, session summaries (by session id), word additions (by word + meaning), tombstones |
| **Monotonic** | Worker head sequence, device status (active → revoked), child status (active → deleted), phone cursor, a phone's own op times (non-decreasing within one day of clock steps) |
| **Derived / recomputed** | box, due, independentAt, firstColdAt, retainedAt, lastAt, lastSession, seenObs, totals, last-8 windows, state labels, word box/due/lastAt |
| **Last-writer-wins (safe)** | profile fields and `helped`, by (effective time, record id). No evidence depends on them. |
| **Explicit handling** | word removal (only the ids the removing phone knew), child deletion (tombstone + family code), learning reset (delete + re-share), reset/generation change, conflicting or malformed data (kept as a local copy, never deleted) |

**Clock handling** (`when()`): the effective time is never before the Worker time the phone had last seen (`after`) and never after the Worker receive time. If the phone's clock differed from the Worker's by more than a day at upload (`ck = 0`), or the record claims a time more than a day after receipt, the record is placed at its receipt time and earns no delay credit. **Delay credit for every record = (recomputed in merged order) AND (granted by the recording phone).** A merge can therefore remove credit but never add it. Imported (quarantined) history lives only inside a base and is never promoted. A base's authority is checked with TR1's `L.trust(memory, receiveTime)`, so authority claimed after receipt is quarantined.

**Known, accepted cost:** same-skill practice uploaded more than 14 days late is ordered at (receipt − 14 days). That can cost the late phone some delay credit. It never adds credit.

### 7.4 Required properties
Every property below is covered by tests. Idempotent: replay is ignored and a retry is acknowledged as a duplicate. Order-independent within the window: 20 shuffles, plus A→B and B→A. Duplicate-safe. Replay-safe: negative control. Bounded storage: checkpoint and caps. Deterministic: property test against a fresh full replay. No mastery inflation or delayed-credit inflation: clock tests plus negative controls. Imported/quarantined evidence never becomes verified.

## 8. Deletion and revocation
| Action | Where | Mechanism | Old offline phone |
|---|---|---|---|
| Remove child from **this phone** | local | Deletes the local copy and remembers the id as "removed here" (records for it are skipped). Refused while changes are unsent. "Hent fjernede barn tilbake hit" downloads it again. | n/a |
| Delete child from **family** | family code | The Worker deletes the child's records, marks the id `deleted` permanently, and stores a tombstone encrypted by the requesting phone. Phones that verify the tombstone delete the child. A server-reported deletion that cannot be verified leaves a local copy. | Its queued records are refused (`child_deleted`). The tombstone removes the child. Nothing comes back. |
| Clear transcript / history locally | local | Unchanged. Transcripts are never synced. | n/a |
| Delete synced learning data (keep child) | family code | "Slett all historikk" on a shared child: delete from family, then share a fresh, empty child with the same profile under a new id. | As above: the old id is a tombstone. |
| Revoke a device | family code | Registry row → `revoked` (permanent for that id). | It gets 403 and keeps local data. Re-enrolling the same id is refused. |
| Reset family / rotate key | family code | Deletes all of the family's Worker data and starts a new generation. | It gets 409 and must enter the new key. Its shared children become local copies, so nothing is lost. |

Tombstones are bounded: one row per deleted child, and at most 100 child rows per family.

## 9. Implementation (this branch)
- `backend/migrations/0001_sync_v1.sql`: four tables (`sync_families`, `sync_devices`, `sync_children`, `sync_records`), with `CHECK` constraints and `UNIQUE(family_id, record_id)`.
- `backend/src/sync.js`: the relay, imported by `index.js` and active only with `SYNC_ENABLED="1"` and `SYNC_DB`. Endpoints, all `POST`: `/sync/status`, `/sync/enroll`, `/sync/push`, `/sync/pull`, `/sync/devices`, `/sync/admin` (`revoke`, `delete-child`, `reset`). Request handling runs in a fixed order:
  1. Feature gate.
  2. Token authentication, before any read.
  3. Per-device rate limit (`SYNC_LIMITER`, falling back to `CHAT_LIMITER` with key `sync:<device>`). Enrol and admin also use pairing's limits.
  4. Streamed body limit (700 KB push, 4 KB admin, 1 KB otherwise).
  5. Exact-key schema check.
  6. Membership check: an active row in the family on the current generation.
  7. Writes guarded in the same transaction (generation, device active, child active, id unused).
  8. Response.

  Per-record results are `ok`, `dup`, `child_deleted`, `child_unknown`, `child_exists`, `quota` or `retry`. Responses never contain the token. Logs are content-free (`{evt:'sync_failure', route, t}`). Quotas: 20 active children, 100 child rows, 200,000 records and 256 MB per family.
- `backend/wrangler.toml`: a new `[env.sync-lab]` (separate Worker name, placeholder D1 id, `SYNC_LIMITER` 120/min). The default (production) environment is unchanged.
- `sync.js` (client, pure core plus injected engine): key codec, HKDF/AES-GCM, strict payload schema, fold, checkpoint, push/pull with retry and resume, share/fork/hide/delete/revoke/reset.
- `sync-ui.js`: the settings section (lab opt-in `spark_sync_lab=1` or sync already on), background rounds (on start, on reconnect, every 5 minutes, after finishing homework; never during an open chat or a provider call), index-safe child removal, and family-wide learning reset.
- `learning.js`: `L.addWord` / `L.reviewWord` (shared by the UI and the merge, identical behaviour) and `mayDelay:false` in `L.event` (the credit cap; live calls never set it).
- `learning-ui.js`, `spark.html`: queue entries next to each live change, written in the same `spark_kids` save. A failed archive save rolls back its queue entries. Plus load-time validation of sync data and the settings section.
- `sw.js`: caches the two new files, generation `spark-learning-20261104-sync1`. CI adds syntax checks, the `sync-lab` dry-run and the browser sync check.

## 10. Failure behaviour
| Failure | Behaviour |
|---|---|
| Endpoint unavailable / offline | Status line only. Changes stay queued. Background retry. Homework is unaffected. |
| D1 unavailable | 503 `unavailable` with a content-free log. The phone is unchanged. |
| Partial request failure / lost reply | The queue entry stays until acknowledged. The retry is acknowledged as `dup` (no duplicate). |
| Interrupted download | The cursor advances only after the downloaded page has been applied and saved. The next download resumes from there. |
| Local storage full | Nothing advances. The next round re-downloads and deduplicates. |
| Malformed server reply | The round is aborted and nothing changes. An undecryptable or invalid record is skipped and counted in the status. |
| Malformed stored sync data / migration problem | The child stays as an unshared local copy. Nothing is deleted. |
| Not paired with the build's Worker | Sync is off and the status explains why. |

## 11. Tests and evidence
- `tests/sync1.test.mjs` (26 tests): the real Worker code on a **real local D1** (workerd through `getPlatformProxy`, `sync-lab` environment, in memory), with real client engines as phones. It covers the 20 required cases, migration from old local-only state, checkpoint equivalence, reset and re-pair, removal from one phone, the feature gate, auth before database access, rate limits, the key codec and associated-data binding. A seeded randomized test (6 seeds × 70 operations on 3 phones, with offline toggles, clock skews and time jumps) checks that every phone's state equals a fresh replay of everything stored, before and after reload. **3 negative controls** each remove one defence (the seen-id check, the Worker clock flag, family scoping in pull) and show that the matching attack succeeds.
- `tests/sync1-frontend.test.mjs` (6 tests, jsdom): default OFF for existing users (no UI, no request, no sync data); the build Worker is the only sync target; backups contain no sync data or key; malformed stored sync data keeps the child; index-safe removal; archive rollback; interaction timestamps stay local.
- `tests/browser-sync-check.mjs` (real Chromium, 5 independent browser profiles, the real Worker on real local D1):
  - A starts sync in the UI on a phone with an existing child. B joins with the typed key.
  - Both go offline, and both do real practice and word-list entry in the UI.
  - A reconnects through the `online` event, then B, then A. They converge. After reloading both, they are still converged, and another round is idempotent.
  - A stale phone C rejoins without erasing newer evidence.
  - C is revoked through the device list and keeps its data.
  - A new phone D joins and converges.
  - The family deletes the child. B follows, and an offline D with queued practice cannot bring it back.
  - A signed Trusted Backup is restored on a new phone E and shared. B receives it as `SITTER` with no duplicated evidence.
  - Request bodies carry no names, words, token or key.

## 13. Approximate scale: 2 children, 3 phones, 1 year
These estimates use measured record sizes: a skill op is about 470 B on the wire, a session summary with 6 events about 1.8 KB, and the base of a year-old child (12 skills, 40 words) about 29 KB.
- **Assumptions:** about 200 homework/practice sessions per child per year, with about 8 learning ops each. That gives roughly 1,800–2,000 records per child per year, or **about 4,000 per family per year**.
- **D1 storage:** about 3–4 MB per family per year, including session summaries and indexes.
- **Requests:** about 10 rounds per phone on a day of use, at 1–3 requests each. That is roughly 20–60 requests per family per day, a few times what chat already uses. A new phone's first download after a year is about 20 pages.
- **D1 rows:** a few rows read per idle pull, and about one row written per record. The free tier allows 5 M reads and 100 k writes per day and 5 GB of storage. A family uses well under 0.1 % of each.
- **Phone storage:** per child, a checkpoint of about 30 KB, a 14-day log of about 30–60 KB, and seen ids of about 40 KB per year (capped at 30,000 ids).
- **First relevant Cloudflare resource:** creating the **D1 database** itself (`wrangler d1 create`, plus migrations). Usage stays inside the free tier by orders of magnitude. If anything is ever metered first, it is D1 rows read, through frequent idle pulls from many phones.

## 17. Exact blockers before production
1. **Product decisions:**
   - (a) whether tutor notes (`notes`) and the parent teaching log (`log`) should sync. Both are provider-generated text; V1 keeps them local.
   - (b) whether two pre-existing local profiles of the same child, made on different phones before sync, should be merged. V1 never merges automatically: they stay separate children, and the parent can remove one.
   - (c) the UX of typing a 28-character key on each phone. QR transfer would need a scanner.
   - (d) whether sync revocation should also block `/chat` for that device. Today chat is revoked only through `REVOKE_BEFORE`.
2. **Operator steps** (not done, by mandate):
   - Create a D1 database.
   - Paste its id in `[env.sync-lab]`, or move the binding to production after a decision.
   - Apply migrations.
   - Set `SYNC_ENABLED="1"` for the chosen environment.
   - Confirm that the app build's `DEFAULT_SERVER_URL` points to that Worker.
3. **Key rotation in place.** V1 rotation is a family reset (server data is deleted and phones re-share). Re-encryption without a reset is not implemented.
4. **Withheld-record detection on new phones.** It would need client-signed heads.
5. A real-phone trial: two phones, airplane mode, and storage pressure on iOS Safari (where localStorage is not guaranteed under pressure).
