# Spark SYNC1 — Privacy-First Multi-Device Sync V1

Status: **implementation candidate on an isolated branch. Not merged, not deployed. Default OFF.** No Cloudflare resource, database or secret has been created. Production configuration and behaviour are unchanged: production has no `SYNC_DB` binding and no `SYNC_ENABLED`, so every `/sync/*` path answers 404 there exactly like an unknown route.
Baseline: `main` at `f4f55af9fd72c5f30a7dc9ade97a01cefa06c48a` (INT1).
Blocker burndown B2 (this revision) repairs the five production blockers listed in §16.1: generation-atomic delete, generation-atomic child creation, unhide beyond the dedupe window, revocation across reset, and local-copy provenance through backup. §16.1 states the invariants, the reproducers and what is still open.

## 1. Goal and non-goal
The same child can use Spark on several family phones. Structured learning progress converges. No phone can silently erase newer progress from another. Offline use keeps working, and sync failure never blocks homework. Existing single-device users and Trusted Backup (TR1) keep working. Raw conversations and photos are never uploaded. A server compromise exposes as little child data as practical.

The goal is **not** "sync everything". V1 syncs the smallest domain that gives continuity: profile basics, learning evidence and its derived mastery, the word list, and bounded session summaries.

## 3. Threat model

| Threat | V1 outcome |
|---|---|
| **Stolen phone** | The thief has the local data (already true today), the device token and the sync key. Parent operations are rate-limited per device, so the stolen phone cannot use up the parent's budget and block the revocation. Until the parent revokes the phone, it can still read the family's synced data and write evidence. It **cannot** revoke other phones, delete children or reset the family: those need the family code, which phones do not store. After revocation it gets 403 and cannot re-enrol (revocation is permanent for that device id, also across a family reset), and re-pairing needs the family code. There is no remote wipe. To also make the stolen key useless against a future server leak, the parent rotates it with "Start på nytt med ny nøkkel". |
| **Stolen device token only** | It cannot enrol for sync without the family key: enrolling needs a membership proof derived from the key. If the token belongs to an already enrolled phone, the thief can download ciphertext and upload records. Uploaded records that do not authenticate are skipped by every phone. Until the phone is revoked, though, such junk uses the family's quotas: active children (20) and records/bytes. Deleted children do not count. Their ids and tombstones are pruned to the newest 100. Revoke the phone. |
| **Family code disclosed** | The holder can pair a new device, revoke phones, delete the server copy of a child, and reset the family's server data. These are availability attacks. They **cannot** read synced data, because the code gives no key. They **cannot** delete local data: a tombstone must authenticate under the family key, and phones keep an unverifiable deletion as a local copy. Rotate `FAMILY_CODE`. |
| **Malicious paired device with the key** | It is inside the trust boundary, as with TR1. It can write arbitrary evidence and inflate mastery, and it can edit profiles. It cannot delete or revoke without the family code. |
| **Worker compromise** (code, secrets, D1) | **Exposed:**<br>• that a family exists;<br>• device ids, enrolment dates and last-seen days;<br>• child ids and the number of children;<br>• when each child was shared and deleted;<br>• for every record: its child id, kind (`base`/`op`/`tombstone`) and Worker receive time — a per-child timeline of when phones uploaded;<br>• (active attacker) which device uploads which child's records, because every push carries the device token;<br>• the clock-agreement flag;<br>• ciphertext sizes, rounded up to 256 encrypted bytes;<br>• the SHA-256 of the membership proof;<br>• tombstone ciphertexts of earlier generations.<br>An active attacker also sees each phone's clock reading (`clientNow`) and membership proofs at enrolment. A proof is an HKDF output: it does not reveal the encryption key.<br>**Not exposed:** names, ages, interests, answers, skills, words, session summaries.<br>**What it can do:** withhold or delete records (availability) and mint tokens. Receive time, clock flag and sequence are not authenticated, so it can also **re-order and re-time records**. That changes derived mastery (box, delay credit, checkpoints) within the evidence phones actually wrote, and it can raise it: the review reproduced box 1 → 4. **What it cannot do:** read payloads, or forge, alter or move a payload to another child, kind, id or generation (AES-GCM associated data). |
| **D1 read compromise** | As above, without the active capabilities. |
| **Rollback or replay of old state** | A record that a phone has already incorporated is ignored: by the per-child watermark (every record at or below it, whatever the history length) and, above it, by the unfolded log and a small recent-id window. A payload moved to another id, child, kind or generation fails AES-GCM authentication. A phone never discards local data because the server sent less. An older server state cannot shrink a phone's state, because records are only added. A brand-new phone can be served a stale but authentic subset. Without client-signed heads this is not detectable (§11). |
| **Forged client** | The same as a malicious device: it is inside the trust boundary. All inputs are schema-checked on both sides, so it cannot inject properties or crash other phones. |
| **Device clock manipulation** | See §7.3. Delay credit can never exceed what the recording phone granted. A phone whose clock disagrees with the Worker at upload, or that claims a time after receipt, gets its records placed at the Worker receive time with no delay credit. Records cannot be placed before the phone's last sync. |
| **Concurrent offline edits** | Evidence is a union of immutable events. Derived state is recomputed. Profile fields are last-writer-wins by effective time. Word removal is scoped to the word ids the removing phone knew (§7). |
| **Duplicated / restored device** (cloned storage) | Record ids are random, not counters, so clones never collide. Identical queued records deduplicate by id. A phone rolled back to an older copy of its own storage re-downloads, deduplicates and converges. |
| **Deleted child** | A tombstone plus a `deleted` status. Records for that id are refused, so an old offline phone cannot resurrect the child (§8). The newest 100 deleted ids are kept. Beyond that, see review-3 F4 and F9 in §16. |
| **Cross-family leakage** | Every row carries `family_id`, derived on the Worker as an HMAC of a fixed label under `DEVICE_SIGNING_SECRET`. It never comes from a request. Every query is scoped by it. A token from another family fails signature verification. Tested with two families on one shared database, plus a negative control that removes the scoping. |
| **Enumeration** | Child, record and generation ids are 128-bit random values. Device ids are UUIDv4 values from the token. An unknown child id gets the same answer whether it exists in another family or nowhere. |

### What V1 protects
- Confidentiality of synced learning content against the Worker, D1, Cloudflare account access and network observers, provided the phones and the app code are not compromised.
- Integrity and authenticity of every synced record against anyone without the family key, including the Worker.
- No family-wide destructive action without the family code. No destruction of local data by anyone without the key.
- Convergence: phones holding the same records, with the same Worker metadata, compute identical state (property-tested).
- **With an honest relay:** no mastery inflation from merging, and no delay credit beyond what the recording phone granted. A compromised Worker can re-time records and so change derived mastery. It cannot change evidence content.

### What V1 does not protect
- A phone or a key holder acting maliciously. The client is the trust boundary, exactly as in TR1.
- Availability against a compromised Worker or a family-code holder.
- The integrity of *derived* mastery against a compromised Worker, which can re-order records (see the table above).
- Detection of withheld records on a brand-new phone.
- Metadata: activity timing, counts and sizes are visible to the Worker.
- Compromise of the GitHub Pages app code. Malicious app code could exfiltrate the key.
- **Not forward secrecy.** A revoked phone that keeps the key can decrypt any ciphertext it obtains later until the key is rotated.

## 4. Storage choice: **D1** (one database, isolated `sync-lab` environment)

| | D1 | Durable Objects | KV |
|---|---|---|---|
| Consistency | Serialized SQLite writes, transactional `batch` | Strong, single-writer per object | Eventual (up to about 60 s); no compare-and-swap |
| Ordering / idempotency | Per-family sequence and `UNIQUE(family_id, record_id)` inside one transaction | Possible, but hand-built | No atomic multi-key writes; LWW per key |
| Revocation / tombstones | Read-your-writes | Yes | A stale read can serve a revoked device or miss a tombstone |
| Offline merge | Server is a relay; merging happens on the client | same | same |
| Queries | Range by sequence; parent admin through SQL (`wrangler d1 execute`) | Custom code, no console | List by prefix (eventual) |
| Ops / migration | Versioned SQL migrations; Time Travel restore | Class + migration tags; data opaque to tooling | Simple, but wrong semantics |
| Cost at family scale | Free tier, far from limits (§13) | Free tier with SQLite DOs | Free tier |
| Privacy | Ciphertext + minimal metadata | same | same |
| Testability here | Real local D1 via workerd (`getPlatformProxy`) in Node and Chromium tests | Needs a DO harness | Easy, but cannot show the needed guarantees |

**Why D1:** the relay needs exactly four things. A gap-free per-family order. Idempotent inserts. Conditional writes that re-check revocation, deletion and generation inside the transaction. A small SQL surface the parent-operator can inspect. D1 gives all four. Because each family runs its own Worker, the main advantage of Durable Objects (an object per tenant) buys nothing here, while it would add a class, migration tags and harder testing. KV is rejected because eventual consistency breaks revocation, tombstones and cursor completeness. No multi-storage abstraction was built.

## 5. Privacy / encryption decision: **hybrid — end-to-end encrypted payloads, minimal server-readable metadata**

Compared options:
1. **Server-readable structured state.** Simplest. But a Worker or D1 compromise exposes the child's whole learning history. The privacy cost is not needed, because the server never has to read content (merging happens on the client, §7).
2. **Fully client-encrypted state blobs.** The server cannot authorize per child, order records or keep tombstones. Each phone would upload whole-state blobs, which forces last-writer-wins on state. That is exactly what destroys independent progress.
3. **Hybrid (chosen).** Every payload is ciphertext. The server sees only what it needs to authorize and order: family, device, child id, record id, kind, sequence number, receive time, a clock flag and size.

Because the merge model is an append-only event log folded deterministically on each phone, end-to-end encryption costs little extra complexity, and it gives the largest real privacy gain available.

**Key ownership and distribution (exact):**
- **Family sync key:** 128 random bits, generated with `crypto.getRandomValues` on the phone that starts sync. It is shown once as 28 Crockford-base32 characters in 7 groups (`XXXX-…`). The last 2 characters are a 10-bit SHA-256 checksum, so a typing error is caught on the phone. The parent types it on each other phone. It is stored in `spark_sync` (localStorage), like the device token. It is never sent to the Worker, never put in backups and never logged.
- **Derivation:** HKDF-SHA-256 (salt `SPARK-SYNC-V1`). `info="enc"` gives an AES-256-GCM key (non-extractable `CryptoKey`). `info="member"` gives a 256-bit membership proof. The Worker stores only `SHA-256(proof)`.
- **Encryption:** AES-256-GCM with a random 96-bit IV for each record. The plaintext is padded to 256-byte buckets. The associated data is `SPARK-SYNC-V1 \n generation \n child \n kind \n record id`. Only standard Web Crypto primitives are used.
- **Enrolment:** a device token (family code, at pairing) plus the membership proof (key). Starting a family additionally needs the family code.
- **Rotation / lost key:** "Start på nytt med ny nøkkel" (family code). It deletes everything the family stored on the Worker and starts a new generation under a new key. Each phone keeps its data. Previously shared children become local copies. The resetting phone shares its children again under new ids, and the other phones join with the new key. V1 does not re-encrypt in place (§17).
- **New phone:** pair with the family code, then enter the sync key. Everything arrives.
- **All phones lost:** the parent's written-down key plus the family code recover everything on a new phone. Without the key the server copy is unreadable by design. Trusted Backup files remain an independent recovery path.
- **Trusted Backup interaction:** none in the key model. Backups contain no key and no sync data.

Why this tradeoff is acceptable: the extra burden is one 28-character code per extra phone. Anything weaker (a key derived from the family code, or a key wrapped by it) would put the key within reach of the Worker, which holds `FAMILY_CODE`. That would void the main protection.

## 6. Family / device / child identity
- **Family namespace:** `family_id = base64url(HMAC-SHA256(DEVICE_SIGNING_SECRET, "SPARK-SYNC-FAMILY-V1"))`. It is one per deployment, derived only on the Worker, and stable across `FAMILY_CODE` rotation. Rotating `DEVICE_SIGNING_SECRET` (which re-pairs every phone anyway) starts a fresh namespace.
- **Family generation:** a random id created by "create" and "reset". It is bound into every ciphertext's associated data. A phone on an old generation gets 409 and must join with the new key.
- **Device identity:** the `deviceId` inside the existing Worker-signed token. TR1's token model is unchanged and `/chat` is untouched. Sync adds a server-side registry row per family (`active` or `revoked`).
- **Child identity:** a random 128-bit id, assigned when a parent shares the child. It is persisted in the same atomic `spark_kids` write as the share and never changes afterwards. Display names are never identities. Existing local children get their id at the moment they are shared. Unshared children keep working exactly as before and need no id.
- **Discovery on a new phone:** after joining, the phone downloads the family log. Each child begins with its encrypted base record, and that record creates the child on the phone. If the phone only has the empty starter profile, the first family child replaces it.
- **Is the family code enough to join?** No. Pairing needs the family code, and sync membership needs the key. Each covers what the other cannot.
- **Revocation:** done by any enrolled phone together with the family code. It is permanent per device id, including across a family reset: a reset never reactivates a revoked row, and a revoked phone cannot run a reset to undo it. The only way to lift it for the same id is the explicit parent operation `reauthorize` (family code), which makes the device *inactive*, not a member: it must still prove the family key. Replacing a phone needs none of that: pairing it again gives a new device id that only needs the key. A revoked phone keeps its local data and gets a clear status. It keeps chat access, which is governed by the existing token and `REVOKE_BEFORE` (§17).
- **Device registry (B4):** a row per device id with `status` (`active`/`revoked`) and `gen`, the generation whose key the device last proved. A device is a *member* only while `status='active'` and `gen` equals the family's current generation. A reset replaces the generation and keeps every row: earlier devices become *inactive* (listed, revocable, must prove the new key). Bounds: the newest 50 inactive rows, revoked rows for 366 days (a device token lasts 365 days from pairing, never later than enrolment, so an older revocation can no longer matter), and a hard cap of 200 rows that refuses a *new* device with `quota` (507) but never an already-known device and never a reset.
- **Trust root:** sync talks only to `DEFAULT_SERVER_URL`, the Worker the app build ships with. It runs only when the phone is paired with that Worker (as TR1 signing does), with `redirect:'error'`. The ⚙️ server address is never used. The server is a relay, not an authority: integrity comes from the key.

## 7. Merge / convergence model

### 7.1 Records
| Server kind | Payload types (inside the ciphertext) |
|---|---|
| `base` | Genesis snapshot of a child when shared: profile, plus learning as the phone holds it (skills, words, totals; sessions travel separately). Exactly one per child, enforced by the Worker. |
| `op` | `skill` (the observed input of one `L.event` and the delay credit the recording phone granted), `word-add`, `word-review`, `word-remove` (explicit ids), `helped`, `session` (summary), `profile` |
| `tombstone` | `{child, t}`, created only by the family-code-gated delete |

### 7.2 Fold
A child's state is: its base, then its other records sorted by `(orderKey, Worker sequence, record id)`, then this phone's unsent changes in local order. `orderKey = max(effectiveTime, receiveTime − 14 days)`, and the base always sorts first. Every input is record data or Worker metadata, so every phone holding the same records computes the same state, whatever order the records arrived in. For uploads within 14 days of recording, the fold is in true time order, independent of upload order. This is tested both ways (A-first vs B-first) and with 20 shuffles.

**Local checkpoints keep phone storage bounded.** After a complete download, every record with `orderKey ≤ WorkerNow − 14 days − 1 day` is final: any record that arrives later sorts after it. Those records are folded into a checkpoint and dropped from the local log. Since a checkpoint is a prefix of the same sequence on every phone, a phone with checkpoints equals a fresh phone that replays everything (tested).

### 7.3 Field classification
| Behaviour | Fields |
|---|---|
| **Append / union** (immutable, deduplicated by record id, and by evidence id in `L.event`) | skill evidence and observations, word reviews, session summaries (by session id), tombstones. Word additions merge by word + meaning: when two phones add the same word, the later id becomes an alias, so its reviews and removals still apply. Residual: a merge that takes the family past the 60-word list limit drops the words beyond it, together with their reviews. |
| **Monotonic** | Worker head sequence, device status (active → revoked), child status (active → deleted), phone cursor, a phone's own op times (non-decreasing within one day of clock steps) |
| **Derived / recomputed** | box, due, independentAt, firstColdAt, retainedAt, lastAt, lastSession, seenObs, totals, last-8 windows, state labels, word box/due/lastAt |
| **Last-writer-wins (safe)** | profile fields and `helped`, by (effective time, record id). No evidence depends on them. |
| **Explicit handling** | word removal (only the ids the removing phone knew), child deletion (tombstone + family code), learning reset (delete + re-share), reset/generation change, conflicting or malformed data (kept as a local copy, never deleted) |

**Clock handling** (`when()`): the effective time is never before the Worker time the phone had last seen (`after`) and never after the Worker receive time. If the phone's clock differed from the Worker's by more than a day at upload (`ck = 0`), or the record claims a time more than a day after receipt, the record is placed at its receipt time and earns no delay credit. **Delay credit for every record = (recomputed in merged order) AND (granted by the recording phone).** A merge can therefore remove credit but never add it. Imported (quarantined) history lives only inside a base and is never promoted. A base's authority is checked with TR1's `L.trust(memory, receiveTime)`, so authority claimed after receipt is quarantined.

**Known, accepted cost:** same-skill practice uploaded more than 14 days late is ordered at (receipt − 14 days). That can cost the late phone some delay credit. It never adds credit.

### 7.4 Required properties
Every property below is covered by tests. Idempotent: replay is ignored and a retry is acknowledged as a duplicate. Order-independent within the window: 20 shuffles, plus A→B and B→A. Duplicate-safe. Replay-safe: negative control. Bounded storage: checkpoint and caps. Deterministic: property test against a fresh full replay. No mastery inflation or delayed-credit inflation: clock tests plus negative controls. Imported/quarantined evidence never becomes verified.

## 8. Deletion and revocation
| Action | Where | Mechanism | Old offline phone |
|---|---|---|---|
| Remove child from **this phone** | local | Deletes the local copy and remembers the id as "removed here" (records for it are skipped). Refused while changes are unsent. "Hent fjernede barn tilbake hit" downloads it again. | n/a |
| Delete child from **family** | family code | The Worker deletes the child's records, marks the id `deleted` permanently, and stores a tombstone encrypted by the requesting phone. Phones that verify the tombstone delete the child. A server-reported deletion that cannot be verified leaves a local copy. | Its queued records are refused (`child_deleted`). The tombstone removes the child. Nothing comes back. |
| Clear transcript / history locally | local | Unchanged. Transcripts are never synced. | n/a |
| Delete synced learning data (keep child) | family code | "Slett all historikk" on a shared child: delete from family, then share a fresh, empty child with the same profile under a new id. | As above: the old id is a tombstone. |
| Revoke a device | family code | Registry row → `revoked`. Permanent for that id, across resets. A revoked phone cannot run a reset or a join to undo it (B4; this replaces review-3 F8's exception). The only lift is `reauthorize` (family code), after which the device still has to prove the key. A reset keeps non-revoked rows as *inactive*, so a lost phone stays listable and revocable (B4; this repairs F7). | It gets 403 and keeps local data. Re-enrolling the same id is refused. |
| Reset family / rotate key | family code | Always possible: it is the way out of a lost key, a full family or a corrupt stored key. The resetting phone first runs a sync round. It shares its children again automatically only if two things hold. First, that round downloaded completely, to the Worker's head, in the current generation, not stopped by the page budget. Second, the Worker's reset reply confirms (`prev`) that this reset replaced exactly that generation, so no other parent phone reset in between (review-3 F1/F2). Otherwise they stay as local copies. The Worker then deletes the family's records and active children and starts a new generation. Kept: every device row (earlier ones become inactive; revoked ones stay revoked), deleted child ids, and tombstones of every generation. | It gets 409 and must enter the new key. On re-joining it receives the old tombstones and verifies them with its previous key: children deleted before the reset are removed. Other shared children become local copies, so nothing is lost. **Local copies are never shared in bulk.** They are shared only one at a time, after a warning that the child may have been deleted from the family. A child deleted in a *later* generation than the phone knew cannot be verified by that phone. The rule above is what keeps it from coming back silently. |

Tombstones are bounded: the newest 100 deleted ids and tombstones are kept, and they do not count toward the 20-child quota. A phone that missed more than 100 deletions and still holds an older one gets `child_unknown` for its ops and keeps it as a local copy that is never shared automatically. A retried *base* for a pruned id is accepted as a new child (F4, §16.1 #3).

## 9. Implementation (this branch)
- `backend/migrations/0001_sync_v1.sql`: four tables (`sync_families`, `sync_devices`, `sync_children`, `sync_records`), with `CHECK` constraints and `UNIQUE(family_id, record_id)`.
- `backend/migrations/0002_sync_v1_blockers.sql` (B4): `ALTER TABLE sync_devices ADD COLUMN gen TEXT NOT NULL DEFAULT ''`. Nothing is deployed, so this is simply the second migration in the first database.
- `backend/src/sync.js`: the relay, imported by `index.js` and active only with `SYNC_ENABLED="1"` and `SYNC_DB`. Endpoints, all `POST`: `/sync/status`, `/sync/enroll`, `/sync/push`, `/sync/pull`, `/sync/devices`, `/sync/admin` (`revoke`, `reauthorize`, `delete-child`, `reset`). Request handling runs in a fixed order:
  1. Feature gate.
  2. Token authentication, before any read.
  3. Per-device rate limit (`SYNC_LIMITER`, falling back to `CHAT_LIMITER` with key `sync:<device>`). Enrol and admin also use pairing's limits.
  4. Streamed body limit (700 KB push, 4 KB admin, 1 KB otherwise).
  5. Exact-key schema check.
  6. Membership check: an active row in the family on the current generation.
  7. Writes guarded in the same transaction. Every write batch carries the same SQL conditions (the device is a member of *this* generation, the child is active, the record id is unused) in each statement, so the check and the write are one database step and a reset, revocation or deletion that lands after the Worker's reads leaves no trace. The child's `active→deleted` flip is the last statement of a delete-child batch and its changed-row count is the outcome; a push that stored nothing re-checks membership and answers 409/403 instead of a silent "retry" (B1, B2).
  8. Response.

  Per-record results are `ok`, `dup`, `child_deleted`, `child_unknown`, `child_exists`, `quota` or `retry`. A child row is created only together with its base, only while the family has room (counted inside the same statement, so concurrent first pushes cannot exceed 20), and a child row left without a record is removed in the same batch. Responses never contain the token. Logs are content-free (`{evt:'sync_failure', route, t}`). Quotas: 20 active children, 100 child rows, 200,000 records and 256 MB per family.
- `backend/wrangler.toml`: a new `[env.sync-lab]` (separate Worker name, placeholder D1 id, `SYNC_LIMITER` 120/min). The default (production) environment is unchanged.
- `sync.js` (client, pure core plus injected engine): key codec, HKDF/AES-GCM, strict payload schema, fold, checkpoint, push/pull with retry and resume, share/fork/hide/delete/revoke/reauthorize/reset. Each shared child keeps a watermark `wm` (B3): every record of that child with Worker sequence ≤ `wm` is already part of its checkpoint or log. It is written in the same `spark_kids` save as the records it describes, so a repeated download is harmless whatever the history length. Checkpoints run page by page during a download, so local storage stays bounded however long the family history is.
- `learning-ui.js` (B5): a local copy exports as `origin:'local-copy'` and imports as `fork:true` (§16.1).
- `sync-ui.js`: the settings section (lab opt-in `spark_sync_lab=1` or sync already on), background rounds (on start, on reconnect, every 5 minutes, after finishing homework), index-safe child removal, and family-wide learning reset. A background round never *starts* during an open chat, a provider call or on the settings page. On the settings page a background change could otherwise be written back by «Lagre» as a stale edit, so only the page's own buttons sync there, and they re-render the form. A round that has already started can finish after the child opens homework. Replacing learning state then is harmless. A family deletion arriving at that moment ends the open session view. If `sync.js`/`sync-ui.js` fail to load, no-op fallbacks in `spark.html` keep the app working as before (tested).

## 10. Failure behaviour
| Failure | Behaviour |
|---|---|
| Endpoint unavailable / offline | Status line only. Changes stay queued. Background retry. Homework is unaffected. |
| D1 unavailable | 503 `unavailable` with a content-free log. The phone is unchanged. |
| Partial request failure / lost reply | The queue entry stays until acknowledged. The retry is acknowledged as `dup` (no duplicate). An acknowledgement that does not match the request ids aborts the round. |
| Family child quota reached | The new child stays shared with its records queued, and the status shows that the quota is full. It is never forked silently. |
| A change that cannot be queued | The child (which already holds the change locally) leaves the family log and stays on the phone as a local copy. The change is never lost at the next fold. |
| Interrupted download | The cursor advances only after the downloaded page has been applied and saved. The next download resumes from there. |
| Local storage full | Nothing advances. The next round re-downloads; every record at or below the child's watermark is recognised as already incorporated. |
| Reset (or revocation) lands between a request's checks and its write | The write conditions fail inside the transaction: nothing is stored, no child row, no tombstone. The phone gets 409 (rejoin) or 403 (revoked). Its queue is intact. |
| Lost reply to a delete-child | The retry is acknowledged as deleted (already deleted in this generation); nothing changes. |
| Lost acknowledgement, download delivers the record first | The download is the acknowledgement: the record leaves the queue and is applied once. |
| Malformed server reply | The round is aborted and nothing changes. An undecryptable or invalid record is skipped and counted in the status. |
| Malformed stored sync data / migration problem | The load-time shape check, or a fold that fails on deeper corruption, leaves that child as an unshared local copy. The round continues for the other children. Nothing is deleted. |
| Not paired with the build's Worker | Sync is off and the status explains why. |

### 11.1 Privacy evidence: why there is no substring scan over ciphertext (CI run 41882703763)
GitHub Actions run 41882703763 failed at `browser-sync-check.mjs:154` with `/sync/push carries Ada`. **This was a test defect, not a leak.**
- **Cause.** The check ran `body.includes("Ada")` (and `"hus"`) over request bodies whose record payloads are AES-256-GCM ciphertext in base64url. A fixed 3-character string occurs at a given random base64url position with probability 64⁻³ = 1/262,144. One browser run sends about 10,400 opaque characters, so each 3-letter word matched by chance in about 4 % of runs. With two such words, about 7.6 % of runs failed with no leak.
- **Evidence.** 27 browser runs were captured and every string in every request was classified. No name or word ever appeared outside an opaque id/IV/ciphertext field. The 2-letter control `Bo` appeared 80 times inside ciphertext, IVs and ids, against about 68 expected by chance. A deterministic Node test (`sync1-privacy.test.mjs`, "CI-flake reproduction") seals a payload for a child named «Bo» with the real codec and counter IVs until the ciphertext contains `Ada`. The old scan fails on it. The new proof accepts it, and decryption shows `Ada` is nowhere in the plaintext.
- **What the tests prove now** (`tests/sync-privacy.mjs`, used by the browser check, the Node privacy tests and test 18-19):
  1. Every request body is a JSON object whose keys are **exactly** the permitted server-readable schema of its endpoint and operation:
     - `status {v}`
     - `enroll {v,mode,proof[,code]}`
     - `push {v,gen,clientNow,records[{id,child,kind,iv,ct}]}`
     - `pull {v,gen,cursor}`
     - `devices {v,gen}`
     - `admin` revoke, delete-child or reset.

     No plaintext field can sit next to the ciphertext.
  2. Every value is an opaque id, IV, ciphertext or proof, a fixed enum, an integer or a device UUID. The family code is accepted only on `enroll create` and `admin`, where the Worker must check it.
  3. The device token appears only in the sending phone's `Authorization` header. The key is sent only as its HKDF member proof, which is checked against a derivation of the known key.
  4. Every sent and every stored ciphertext opens with the family key through the real codec (authenticated AES-GCM bound to generation, child, kind and id, then the exact payload schema). The child's name, interests, words and meanings are present **only after** decryption.
  5. A bit flip, or the same ciphertext presented for another child, id, kind or generation, fails authentication.
  6. Only long secrets are excluded by substring: the token, and the key with and without separators (at least 28 characters, chance match below 2⁻¹⁶⁰). Short words are never searched for in ciphertext.
- **Negative controls.** Each of these is rejected:
  - the real engine patched to add `name: kid.name` to every push (Node);
  - `name`/`interests`/`word`/`meaning`/`summary`/`transcript`/`image`/`notes`/`log` added at the top level or to a record;
  - unencrypted base64url JSON in place of `ct` (fails decryption);
  - the token or the key in the body;
  - another phone's token in the header;
  - the raw key in place of the proof;
  - the family code on a normal request.

  The browser check repeats the first two controls on the requests it actually captured.
- **Repetition.** After the repair, `browser-sync-check.mjs` passed **25 of 25** consecutive local runs with genuine random keys, ids and IVs. The old scan would be expected to fail about 2 of 25. GitHub Actions run 41890021287 (head `f7e6f85`) passed every step, including this check.

## 13. Approximate scale: 2 children, 3 phones, 1 year
These estimates use measured record sizes: a skill op is about 470 B on the wire, a session summary with 6 events about 1.8 KB, and the base of a year-old child (12 skills, 40 words) about 29 KB.
- **Assumptions:** about 200 homework/practice sessions per child per year, with about 8 learning ops each. That gives roughly 1,800–2,000 records per child per year, or **about 4,000 per family per year**.
- **D1 storage:** about 3–4 MB per family per year, including session summaries and indexes.
- **Requests:** about 10 rounds per phone on a day of use, at 1–3 requests each. That is roughly 20–60 requests per family per day, a few times what chat already uses. A new phone's first download after a year is about 20 pages.
- **D1 rows:** a few rows read per idle pull, and about one row written per record. The free tier allows 5 M reads and 100 k writes per day and 5 GB of storage. A family uses well under 0.1 % of each.
- **Phone storage:** per child, a checkpoint of about 30 KB, a 14-day log of about 30–60 KB, and a recent-id window of at most 10,000 ids (up to about 190 KB per child, no longer growing with history). All of it lives inside `spark_kids` (one atomic write) and competes with homework saves for the browser's localStorage quota (about 5 MB).
- **First relevant Cloudflare resource:** creating the **D1 database** itself (`wrangler d1 create`, plus migrations). Usage stays inside the free tier by orders of magnitude. If anything is ever metered first, it is D1 rows read, through frequent idle pulls from many phones.

### 16.1 Production-blocker burndown B2 (this revision)
**Invariants written before editing, and enforced by tests:**
- *Generation isolation:* a mutation started against generation N never creates authoritative N+1 state (the explicit exception: revocations carry over a reset by design).
- *Delete:* a family-deleted child id is never accepted again while its row exists; delete-child is atomic with the generation check and idempotent.
- *Active quota:* only active children count toward the 20; deleted, tombstoned and ghost state cannot occupy a slot; the count is taken inside the creating statement.
- *Reset liveness:* an authorized reset is possible whatever the quota, child or registry state.
- *Revocation:* explicit revocation survives a reset; only `reauthorize` (family code) lifts it, and even then the key is still needed. The registry is bounded.
- *Unhide / truncation:* a repeated download reconstructs the current family state exactly once, for any history length. Bounded dedupe state never turns an old applied record into new evidence.
- *Authority:* no replay, reset, restore or re-share path adds verified mastery, delayed credit, word-review credit or session evidence.
- *Provenance:* a known local copy does not become an ordinary profile by crossing backup/restore.

At a 2,000-id window that took about a year of use. | **Mitigated, residual.** Window raised to 10,000 ids (the original attack needed >30,000). The real fix needs an authenticated per-record order or an op id inside word-review evidence (learning schema change): listed in §17. Needs a compromised Worker and a key-holder's old record. |
| 2 | Low | Revoked rows count toward the 200-row cap and last 366 days, so a parent who revoked about 150+ devices and then reset cannot add a *new* device until they age out. | Residual (parent-caused, extreme). Existing devices and reset still work. Remedy: rotate `DEVICE_SIGNING_SECRET` (fresh namespace). |
| 3 | Low | A deleted child returns after more than 100 later deletions pruned its row (F4), via a retried base with a lost acknowledgement. The answer to a base for a pruned id is `ok`, not `child_unknown`. | Residual (F4, unchanged). §8 wording corrected. |
| 4 | Low | An `unhide` (or `hide`) made while a sync round is running is overwritten by that round's saved state. Nothing is applied twice or skipped; the parent repeats the action. | Residual, pre-existing. |
| Info | | A key holder racing two different bases for one child id stores two bases (the lowest sequence wins, the fold is deterministic); the inactive-row prune can drop a lost phone's row after 50 newer inactive devices; no privacy-test traffic sends `reauthorize` (the validator accepts it). | Documented. |

## 17. Exact blockers before production
1. **Product decisions:**
   - (a) whether tutor notes (`notes`) and the parent teaching log (`log`) should sync. Both are provider-generated text; V1 keeps them local.
   - (b) whether two pre-existing local profiles of the same child, made on different phones before sync, should be merged. V1 never merges automatically: they stay separate children, and the parent can remove one.
   - (c) the UX of typing a 28-character key on each phone. QR transfer would need a scanner.
   - (d) whether sync revocation should also block `/chat` for that device. Today chat is revoked only through `REVOKE_BEFORE`.
2. **Operator steps** (not done, by mandate):
   - Create a D1 database.
   - Paste its id in `[env.sync-lab]`, or move the binding to production after a decision.
   - Apply migrations.
   - Set `SYNC_ENABLED="1"` for the chosen environment.
   - Confirm that the app build's `DEFAULT_SERVER_URL` points to that Worker.
3. **Key rotation in place.** V1 rotation is a family reset (server data is deleted and phones re-share). Re-encryption without a reset is not implemented.
4. **Withheld-record detection on new phones.** It would need client-signed heads.
5. A real-phone trial: two phones, airplane mode, and storage pressure on iOS Safari (where localStorage is not guaranteed under pressure).
6. The reset and generation paths have had a third independent review (§16) and the burndown a fourth (§16.1). **Repaired in B2:** delete-child vs reset, the ghost child on a push/reset race (RT-F3), unhide beyond the dedupe window (RT-F2), revocation across reset (F7, F8), local-copy provenance (F10). **Still open before production:** F4 (a deleted child's id after more than 100 later deletions), F5, F6, F9, F11, RT-F4 (all LOW, safe direction except F4), and the §16.1 findings 1-4.
7. **Authenticated order for word-review (§16.1 #1).** A compromised relay can replay an old word-review record under a new sequence once it is older than the 10,000-id window. A real fix needs a per-record op id inside word-review evidence or authenticated sequence numbers.
8. **Prune policy for deleted child ids (F4)** needs either unbounded retention of deleted ids or a per-generation tombstone list checked on base push.
9. **Lost update of `hide`/`unhide` during a running round (§16.1 #4)** and the registry-full case (§16.1 #2) need a small UX/state fix, not a protocol change.
10. **Clock credit (F3).** The Worker accepts a phone clock within ±24 h as "agreeing" for delay credit, so a phone up to a day fast can earn early delayed-review credit that survives the merge. A tighter bound for credit (minutes) than for ordering is a small change, but it is a product trade-off for phones that are legitimately offline.

### 17.1 Product decision matrix (V1 behaviour kept; not decided here)
| Decision | V1 behaviour today | Options | Consequence to weigh |
|---|---|---|---|
| Tutor notes / teaching log sync | Local only (provider-generated text) | Keep local; sync encrypted as new op kinds | More family insight, against more sensitive content on more devices and larger records |
| Merging duplicate pre-sync profiles | Never automatic; separate children; the parent removes one | Keep; guided merge (pick one base, replay evidence) | Duplicate evidence and mastery inflation if done wrong; needs its own design |
| Key entry: QR or typed | Typed 28-character key (checksum, tolerant of confusables) | Keep typed; add QR (needs a camera/scanner path) | UX friction against new code and camera permission |
| Sync revocation also revokes chat | No; chat is revoked only through `REVOKE_BEFORE` | Keep separate; tie the device token's chat access to the sync revocation | One action for a lost phone, against coupling two independent features |
| Clock tolerance for delay credit (F3) | ±24 h (same as ordering) | Keep; separate tighter credit bound | Fewer false credits, against lost credit for phones with drifting clocks |
| Revocability after reset (F7) | **Decided and implemented (B4):** earlier devices stay as `inactive` rows (bounded, §6) | Keep | A lost phone stays listable and revocable; the registry is bounded instead of growing |
